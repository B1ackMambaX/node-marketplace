# Правила работы с node-marketplace

Этот файл действует на весь репозиторий. Перед изменением конкретной папки прочитайте её
`README.md` и README родительских папок. Инструкции пользователя имеют приоритет;
локальная документация уточняет назначение компонентов и ограничения архитектуры.

## Назначение проекта

Учебное REST API маркетплейса для курса «Архитектура программных систем». Стек:
Bun, TypeScript в строгом режиме, Express 5, Prisma ORM 7 и PostgreSQL. Приложение
остаётся одним монолитом с общей БД, но разделено на технические слои и подготовлено
для изучения последующего выделения сервисов.

- B2B — кабинет продавца: товары, SKU и управление физическими остатками.
- B2C — публичный каталог, корзина и заказы покупателей.
- Moderation — заявки на проверку товаров и решения модераторов.
- Docker, фронтенд, платежи, доставка и брокер событий в текущий MVP не входят.

Описание запуска и пользовательских сценариев находится в [README.md](README.md).

## Границы слоёв

- `domain` зависит только от собственного кода. Здесь нет Express, Prisma, Zod,
  платформенных API, переменных окружения или HTTP-статусов.
- `application` зависит от `domain` и собственных интерфейсов в `contracts`.
  Сервисы не импортируют инфраструктуру, HTTP, Prisma или сгенерированные ORM-типы.
- `presentation` зависит от `application` и `domain`. Контроллеры разбирают запросы,
  вызывают сервисы и формируют ответы; не выполняют SQL и не меняют бизнес-состояние напрямую.
- `infrastructure` реализует порты `application`, использует `domain` и внешние библиотеки.
  Репозитории не зависят от HTTP и не принимают бизнес-решения.
- Конкретные зависимости связываются в `src/dependencies.ts`. Новые адаптеры не создаются
  внутри сервисов или контроллеров.
- Ограничения импортов закреплены в `eslint.config.mjs` и `tests/architecture.test.ts`.
  Не ослабляйте их, чтобы обойти неправильное направление зависимости.

## Сохранение поведения

При рефакторинге сохраняйте существующие маршруты и HTTP-контракты, если пользователь
не запросил их изменение. При добавлении или изменении API синхронно обновляйте
контроллер, схему валидации, OpenAPI и соответствующие сценарные тесты.

- API использует `/api/v1`, UUID, JSON-поля в `camelCase` и суммы в целых копейках, RUB.
- Пагинация: `{items, total, limit, offset}`; ошибки: `{code, message, details?}`.
- Проверяйте роль и владельца объекта. Чужие товары и заказы не должны раскрываться.
- Не возвращайте `passwordHash`, хеши сессий, внутренний резерв, себестоимость или
  данные идемпотентности в публичных ответах. Используйте явно заданные поля и мапперы.
- `quantity` включает резерв; доступный остаток равен `quantity - reserved`.
  Физический остаток и резерв не могут быть отрицательными; резерв не превышает остаток.
- Оформление заказа, резерв, снимки цен и очистка оформленной корзины — одна транзакция.
  Отмена и завершение не должны повторно освобождать резерв или списывать товар.
- `Idempotency-Key` относится к покупателю. Повтор ключа с тем же нормализованным телом
  оформления возвращает исходный заказ, с другим телом — конфликт.
- Модерация атомарно меняет заявку и статус товара. Пока товар в `PENDING`, его
  содержимое и SKU неизменяемы. Изменение контента требует новой модерации.
- Пароли хешируются Argon2id; refresh-токены хранятся как хеши и ротируются.
  Публичная регистрация служебных ролей запрещена.

## Правила реализации

- Одна функция или метод отвечает за один понятный шаг; сложные сценарии делите на
  именованные операции. Маршруты содержат только регистрацию обработчиков и middleware.
- Передавайте зависимости через конструкторы и контракты. Не вводите скрытые глобальные
  зависимости в прикладной слой; используйте уже существующий RepositoryContext.
- Проверка формы HTTP-запроса находится в Zod-схемах, бизнес-инварианты — в домене
  и прикладных сценариях, операции хранения — в репозиториях.
- Границы транзакции задаёт сервис, изоляцию, повтор конфликтов и общий transaction client —
  инфраструктурный RepositoryContext. Не отправляйте необратимые внешние действия из callback,
  который может быть выполнен повторно.
- Используйте строгие типы, `import type` для типов, осмысленные имена и явные проверки
  вместо маскировки проблем через `any`, утверждения типов или отключение правил ESLint.
- Следуйте `.editorconfig`, `.prettierrc.json` и `eslint.config.mjs`. Не редактируйте вручную
  `node_modules`, `src/generated`, артефакты сборки или конфигурацию IDE.
- При создании папки добавляйте README с её назначением, содержимым и местными правилами;
  при изменении ответственности папки обновляйте существующий README.

## База данных и окружение

- Конфигурация задаётся через `.env`; пример находится в `.env.example`. Не публикуйте
  секреты, реальные строки подключения и содержимое локального `.env`.
- Изменение структуры БД требует изменения `prisma/schema.prisma` и новой миграции.
  Применённые миграции не переписываются; сгенерированный клиент обновляется командой.
- Seed предназначен для демонстрации и должен сохранять существующие данные при повторном запуске.
- Интеграционные тесты используют отдельный `TEST_DATABASE_URL`; имя БД содержит `test`,
  адрес отличается от рабочей БД. Не очищайте произвольные данные и не используйте рабочую БД.

## Проверки

Команды запускайте из корня проекта после `bun install` и `bun run db:generate`.

```sh
bun run typecheck
bun run lint
bun run format:check
bun run test:unit
bun test
```

`bun run check` выполняет typecheck, ESLint, Prettier и весь набор тестов.
Интеграционная группа выполняется только при настроенном `TEST_DATABASE_URL`.
При изменениях бизнес-сценариев проверяйте сервисы и затронутые HTTP-сценарии;
при изменении репозиториев или транзакций нужна проверка с PostgreSQL.
Для изменений только документации достаточно форматирования Markdown и проверки
ссылок и покрытия папок. Не выдавайте пропущенные или недоступные проверки за успешно
выполненные; в результате работы указывайте реальные ограничения среды.
