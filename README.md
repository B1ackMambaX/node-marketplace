## Запуск без Docker

Нужны Bun 1.3+ и доступный PostgreSQL 14+. Базы данных создайте заранее, например через SQL-консоль PostgreSQL:

```sql
CREATE DATABASE marketplace;
CREATE DATABASE marketplace_test;
```

```sh
bun install
cp .env.example .env
```

В `.env` укажите свои адрес, порт, имя пользователя и пароль PostgreSQL в `DATABASE_URL`. Задайте случайный `JWT_SECRET` длиной не менее 32 символов, например сгенерированный командой:

```sh
bun -e 'console.log(require("node:crypto").randomBytes(32).toString("hex"))'
```

Не публикуйте `.env`. `TEST_DATABASE_URL` в примере закомментирован: включите его только после создания отдельной тестовой БД.

```sh
bun run db:generate
bun run db:deploy
bun run db:seed
bun run dev
```

`db:deploy` применяет включённую в проект начальную миграцию. При последующих изменениях схемы используйте `bun run db:migrate --name <название>`, после чего `bun run db:generate`. Bun сам читает `.env`; Prisma CLI запускается под Bun через `bunx --bun`.

- API: `http://localhost:3000/api/v1`
- Swagger UI: `http://localhost:3000/docs`
- OpenAPI JSON: `http://localhost:3000/openapi.json` — схемы генерируются из Zod; методы, пути, статусы и описания операций заданы явно.
- Проверка процесса: `/health`
- Проверка подключения к БД: `/ready` (`503`, если PostgreSQL недоступен)

`bun run start` запускает сервер без наблюдения за файлами. `PORT` по умолчанию равен `3000`. `SIGINT` и `SIGTERM` прекращают приём новых запросов и закрывают подключения к PostgreSQL.

### Демонстрационные аккаунты

Пароль задаётся в `SEED_PASSWORD` (минимум 12 символов); значение из `.env.example` — `Demo-password-2026`.

| Email                | Роль      |
| -------------------- | --------- |
| buyer@demo.local     | BUYER     |
| seller@demo.local    | SELLER    |
| seller2@demo.local   | SELLER    |
| moderator@demo.local | MODERATOR |
| admin@demo.local     | ADMIN     |

Seed создаёт категории, два опубликованных товара и один черновик. Повторный запуск сохраняет существующие данные, пароли, цены и остатки. Это демонстрационные аккаунты для локального обучения.

## API и правила

UUID используются для идентификаторов, даты возвращаются в ISO 8601, JSON-поля — в `camelCase`. Все цены и суммы — **целые копейки, RUB**. Страницы имеют вид `{items, total, limit, offset}`; `limit` по умолчанию `20`, максимум `100`. Ошибки возвращаются как `{code, message, details?}`. Некорректные поля дают `422`, конфликт бизнес-состояния — `409`, чужой объект — `404`.

### Авторизация

| Метод       | Путь           | Назначение                         |
| ----------- | -------------- | ---------------------------------- |
| POST        | /auth/register | Регистрация BUYER или SELLER       |
| POST        | /auth/login    | Пара access/refresh-токенов        |
| POST        | /auth/refresh  | Одноразовая ротация refresh        |
| POST        | /auth/logout   | Отзыв refresh                      |
| GET / PATCH | /users/me      | Просмотр профиля / изменение имени |

Роли MODERATOR и ADMIN создаются seed-скриптом; публичная регистрация этих ролей запрещена. Access JWT передаётся в `Authorization: Bearer <token>` и действует 15 минут. Refresh действует 7 дней, хранится в БД только в виде SHA-256-хеша. Пароли хешируются Argon2id. Logout отзывает refresh; уже выданный access действует до истечения срока. При каждом авторизованном запросе актуальная роль проверяется по БД.

### Продавцы, категории и модерация

| Метод                | Путь                             | Доступ                                     |
| -------------------- | -------------------------------- | ------------------------------------------ |
| GET / POST           | /seller/products                 | SELLER: свои товары / новый черновик       |
| GET / PATCH / DELETE | /seller/products/:id             | SELLER: свой товар                         |
| GET / POST           | /seller/products/:id/skus        | SELLER: варианты товара                    |
| PATCH / DELETE       | /seller/products/:id/skus/:skuId | SELLER: свой SKU                           |
| POST                 | /seller/products/:id/submit      | SELLER: отправка на проверку               |
| GET                  | /categories                      | Публичный список категорий                 |
| POST                 | /categories                      | ADMIN: создать категорию                   |
| PATCH / DELETE       | /categories/:id                  | ADMIN: изменить / удалить пустую категорию |
| GET                  | /moderation/tickets              | MODERATOR / ADMIN: очередь и история       |
| GET                  | /moderation/tickets/:id          | MODERATOR / ADMIN: снимок и решение        |
| POST                 | /moderation/tickets/:id/approve  | MODERATOR / ADMIN: одобрить                |
| POST                 | /moderation/tickets/:id/reject   | MODERATOR / ADMIN: отклонить с `reason`    |

Категории плоские. Товар содержит описание и URL изображений, SKU — имя, характеристики, цену, необязательную себестоимость и остаток. SKU нужен для вариантов цвета/размера и других характеристик. Загрузка файлов не реализована.

Статусы товара: `DRAFT → PENDING → APPROVED / REJECTED`. Отправка на модерацию явная и требует хотя бы один активный SKU. Заявка сохраняет снимок товара; решение и статус товара меняются атомарно. Отклонённый товар можно исправить и отправить снова. Пока товар в PENDING, его редактирование, удаление и изменения SKU запрещены. Одновременно может существовать только одна открытая заявка на товар.

Изменение текста, категории, изображений, имени или характеристик SKU, добавление или удаление SKU возвращают товар в DRAFT и скрывают его из каталога. Изменение цены, себестоимости и остатка не требует повторной модерации. Цена обновляется в корзинах, но уже оформленные заказы сохраняют свою цену.

`quantity` — физическое количество, **включая резерв**. Доступно для продажи `quantity - reserved`. Резерв меняется только через заказы. Продавец не может установить остаток ниже резерва или удалить товар/SKU с активным резервом. Удаление мягкое: история заказов и заявок сохраняется. Категория с любыми товарами, включая архивные, не удаляется.

У списка своих товаров есть фильтр `status`. У списка заявок — `status` (по умолчанию PENDING) и `productId`. Очередь отсортирована по дате создания.

### Покупки и заказы

| Метод          | Путь                     | Назначение                             |
| -------------- | ------------------------ | -------------------------------------- |
| GET            | /catalog/products        | Публичный каталог                      |
| GET            | /catalog/products/:id    | Публичная карточка                     |
| GET / DELETE   | /cart                    | BUYER: просмотр / очистка корзины      |
| POST           | /cart/items              | BUYER: добавить SKU и количество       |
| PATCH / DELETE | /cart/items/:skuId       | BUYER: установить количество / удалить |
| POST           | /orders                  | BUYER: оформить всю корзину            |
| GET            | /orders                  | BUYER: свои заказы                     |
| GET            | /orders/:id              | BUYER: детали своего заказа            |
| POST           | /orders/:id/cancel       | BUYER: отменить заказ                  |
| GET            | /admin/orders            | ADMIN: все заказы                      |
| PATCH          | /admin/orders/:id/status | ADMIN: PROCESSING или COMPLETED        |

Каталог показывает только одобренные товары с активными SKU, скрывает себестоимость и внутренний резерв. Нулевой доступный остаток не скрывает товар. Фильтры: `search` (подстрока названия без учёта регистра), `categoryId`, `minPrice`, `maxPrice`. Сортировка `sort`: `newest`, `oldest`, `priceAsc`, `priceDesc`. Фильтр цены требует хотя бы один SKU в диапазоне; сортировка цены использует минимальную цену всех активных SKU товара. При равных значениях используется ID для устойчивого порядка.

POST в корзину прибавляет количество, PATCH устанавливает его. Максимум 100 разных SKU, до 10000 единиц одного SKU. Добавление требует доступный товар и достаточный остаток, но **корзина не резервирует** товар. Если после добавления товар скрыли или остатки закончились, GET корзины сохраняет позицию и показывает `available: false`; оформление блокируется.

POST `/orders` принимает `{deliveryAddress}` и обязательный заголовок `Idempotency-Key` (1–128 символов: буквы ASCII, цифры, `_ . : -`). В одной serializable-транзакции выполняются проверка всей корзины, резервирование, создание заказа со снимками цен/названий и очистка оформленных позиций. Любая ошибка откатывает все изменения, корзина остаётся. Сумма заказа ограничена `2147483647` копейками.

Ключ идемпотентности принадлежит покупателю и сохраняется на срок жизни заказа. Повтор ключа с тем же нормализованным адресом возвращает исходный заказ (`200`, первая покупка — `201`), даже если корзина впоследствии изменилась. Другой адрес с тем же ключом даёт `409`. Для нового заказа используйте новый ключ.

Статусы заказа: `CREATED → PROCESSING → COMPLETED`. Покупатель может отменить CREATED или PROCESSING: получится CANCELLED, резерв освобождается, физический остаток остаётся прежним. При COMPLETED уменьшаются и физический остаток, и резерв. Повторная отмена или повтор текущего административного статуса безопасны. Из терминального статуса нельзя вернуться в обработку. Администратор имитирует обработку заказа; оплаты и доставки нет. Списки заказов поддерживают `status`.

## Пример полного сценария

Запросы ниже можно выполнить через Swagger. Во всех защищённых запросах добавляйте Bearer-токен соответствующей роли. Все пути здесь начинаются с `/api/v1`.

1. Войдите продавцом: `POST /auth/login` с `{"email":"seller@demo.local","password":"Demo-password-2026"}`. Из ответа сохраните `accessToken`.
2. Получите `GET /categories` и выберите `categoryId`.
3. Создайте товар через `POST /seller/products`:

```json
{
  "name": "Рюкзак",
  "description": "Городской рюкзак 20 литров",
  "categoryId": "UUID_КАТЕГОРИИ",
  "images": ["https://example.com/backpack.jpg"]
}
```

4. Для полученного ID создайте `POST /seller/products/:id/skus`:

```json
{
  "name": "Чёрный",
  "attributes": { "color": "black" },
  "price": 350000,
  "costPrice": 200000,
  "quantity": 10
}
```

5. Отправьте `POST /seller/products/:id/submit` без тела. Сохраните ID заявки.
6. Войдите модератором и вызовите `POST /moderation/tickets/:id/approve`. Товар появится в каталоге.
7. Войдите покупателем и добавьте `POST /cart/items` с `{"skuId":"UUID_SKU","quantity":2}`.
8. Вызовите `POST /orders`, передав заголовок `Idempotency-Key: demo-order-1` и тело `{"deliveryAddress":"Екатеринбург, Ленина, 1"}`. Заказ стоит 700000 копеек, доступны 8 единиц товара.
9. Повторите тот же запрос: вернётся тот же заказ, доступный остаток не изменится.
10. Войдите администратором и последовательно выполните `PATCH /admin/orders/:id/status` с `{"status":"PROCESSING"}`, затем `{"status":"COMPLETED"}`. Физический остаток станет 8, резерв — 0.

Для сценария отмены создайте другой заказ с новым ключом и вызовите `/orders/:id/cancel` под его покупателем. Проверить текущие остатки можно в кабинете продавца.

## Проверки

```sh
bun run typecheck
bun test
```

Без `TEST_DATABASE_URL` интеграционная группа пропускается; модульные проверки денежных сумм, статусов, PATCH-валидации и OpenAPI выполняются. Для проверки API укажите отдельную БД:

```sh
TEST_DATABASE_URL=postgresql://postgres:postgres@localhost:5432/marketplace_test bun test
```

Интеграционные тесты сами применяют миграции к тестовой БД, создают собственных пользователей и товары с уникальными идентификаторами и удаляют только свои записи. Имя тестовой БД должно содержать `test`, адрес БД должен отличаться от рабочей. Перед тестами нужен сгенерированный Prisma Client (`bun run db:generate`).

Проверяются роли и доступ к чужим объектам, ротация токенов, модерация, публичные данные, поиск/фильтры/сортировка, актуальная цена корзины и снимок цены заказа. Отдельные сценарии проверяют конкурентное оформление с одним ключом, покупку последней единицы двумя покупателями, откат всей покупки, повторную отмену и завершение без двойного списания.

## Слоистая архитектура

```text
HTTP → Controller → Application service → Repository contract
                         ↓                       ↑
                    Domain rules         Prisma repository → PostgreSQL
```

```text
src/
  domain/          модели, константы, бизнес-правила и ошибки
  application/     сценарии, DTO, преобразование результатов, интерфейсы адаптеров
    services/      авторизация, товары, SKU, модерация, каталог, корзина, заказы
    contracts/     интерфейсы репозиториев, транзакций, хеширования, токенов и часов
  infrastructure/  реализации репозиториев, Prisma, JWT, Argon2id, конфигурация
  presentation/    Express, контроллеры, маршруты, Zod-схемы, middleware, OpenAPI
  dependencies.ts   создание и связывание конкретных зависимостей
  app.ts           сборка приложения
  server.ts        запуск HTTP-сервера и завершение процесса
```

**Presentation** разбирает параметры HTTP, проверяет форму входных данных и преобразует ошибки в HTTP-статусы. Контроллеры вызывают сервисы; маршруты только связывают методы, URL, middleware и обработчики. Здесь нет запросов Prisma, SQL или правил управления остатками.

**Application** реализует бизнес-сценарии и определяет границы транзакций. Сервисы получают зависимости через конструкторы, вызывают интерфейсы репозиториев и доменные правила. DTO и мапперы формируют результаты без паролей, себестоимости и внутренних полей там, где эти данные не нужны. Сервисы не импортируют Express, Zod, Prisma, JWT-библиотеки или конкретные адаптеры.

**Domain** содержит независимые модели, правила доступности товара, расчёта денег и переходов статусов. Доменные ошибки описывают причину отказа, без HTTP-статусов. Этот слой не зависит от остальных слоёв и внешних библиотек.

**Infrastructure** реализует порты: строит запросы Prisma/SQL, хранит сессии, подписывает JWT и хеширует пароли. Репозитории отвечают за чтение и запись данных; они не принимают бизнес-решения о публикации товара или допустимости отмены заказа. `PrismaRepositoryContext` создаёт репозитории на одном transaction client, задаёт serializable-изоляцию, повторяет конфликты сериализации и переводит ошибки Prisma в ошибки приложения.

`dependencies.ts` выбирает адаптеры и передаёт их сервисам. HTTP-приложение также можно собрать с собственными зависимостями через `createHttpApp`; при сборке `createHttpApp` соединения с БД не создаются. `RepositoryContext` предоставляет сервисам репозитории для обычного чтения или общей транзакции; PrismaRepositoryContext реализует это через Prisma.

### ESLint и Prettier

```sh
bun run lint
bun run lint:fix
bun run format
bun run format:check
bun run check
```

ESLint использует flat config, рекомендуемые правила TypeScript, проверку неиспользуемого кода, type-only imports, обязательные фигурные скобки и строгие сравнения. Ограничения импортов запрещают домену зависимости от внешних слоёв, сервисам — зависимости от ORM/HTTP, HTTP-коду — обращение к инфраструктуре, а инфраструктуре — зависимости от HTTP. Дополнительно есть тест границ слоёв.

Prettier отвечает за форматирование: отступы в два пробела, одинарные кавычки, точки с запятой, завершающие запятые и ширина строки 100. Сгенерированный Prisma Client, зависимости и миграции исключены из форматирования; generated-код исключён из lint. `.editorconfig` задаёт те же базовые правила для редакторов.

`bun run check` последовательно выполняет typecheck, ESLint, проверку форматирования и тесты. `bun run test:unit` запускает проверки правил, сервисов, архитектуры, документации и валидации без PostgreSQL. Интеграционные тесты сохраняют HTTP-сценарии и проверяют атомарность на реальной БД; тесты сервисов используют интерфейсы репозиториев с подменяемыми реализациями.
