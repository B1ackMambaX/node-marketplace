# Тесты

Проверки поведения приложения и соблюдения архитектурных границ.

## Содержимое

- `order-rules.test.ts` — деньги и переходы статусов.
- `services.test.ts` — прикладные сценарии с подменёнными портами.
- `architecture.test.ts` — направления импортов между слоями.
- `validation.test.ts` и `openapi.test.ts` — входные схемы и документированный контракт.
- `integration.test.ts` — HTTP через Supertest и реальная PostgreSQL-БД.
- [helpers](helpers/README.md) — фикстуры и TestUnitOfWork.

## Правила и ограничения

- Тестируйте наблюдаемое поведение и важные инварианты, а не копию реализации.
- Unit-тесты не должны требовать PostgreSQL или импортировать корневую сборку приложения с конкретными адаптерами.
- Интеграционная группа использует TEST_DATABASE_URL: отдельную БД с `test` в имени, отличающуюся от рабочей.
- Интеграционные тесты применяют миграции и очищают только созданные ими записи; не используйте TRUNCATE общих таблиц.
- Критические сценарии: доступ к чужим объектам, модерация, идемпотентность, конкурентное оформление, откат и однократное изменение резервов.
- Указывайте реально выполненные проверки: пропущенная интеграционная группа не означает проверенную атомарность БД.

## Проверки

После установки зависимостей и генерации клиента: `bun run test:unit` без БД, `bun test` для всего набора. Чтобы включить интеграционную группу, настройте TEST_DATABASE_URL.
